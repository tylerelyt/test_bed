# 架构设计审查

日期：2026-11-13。对象：[岗位 Agent 供应平台设计稿](../README.md)，不等同于运行代码审查；未执行组件联调。结论：现成 Harness、独立上下文供应和独立模型供应的方向符合作者要求，但关键运行约束尚未落实为接口与机制，需修订后作为实施基线。

## AR01 · P1：Agent 创建与启动缺少可靠的控制流程

依据：设计稿第 38 行管理 API 直接请求 Runner；第 186—189 行描述了作业投递、心跳和恢复原则，但没有定义运行创建、启动确认、归属转移与进程退出的具体协议。

场景：Runner 已启动 Harness，返回 API 的响应在网络中丢失；调用者重试时，平台无法按已定义的机制判断应返回原实例还是启动新实例。Runner 心跳暂时失联时，第二个 Runner 也缺少阻止重复执行的明确规则。

需要补充：请求幂等键及数据库唯一约束；期望状态与实际状态；运行领取及有期限的执行归属；启动前后持久化 runtime/session 标识；Runner 按同一标识幂等启动和核对进程；旧执行者的失效处理。API 返回已接受的运行标识，界面查询实际状态。外部动作状态不明时不自动创建第二次执行。

## AR02 · P1：权限没有从企业入口贯穿到实际执行

依据：第 120—122 行发布包包含授权和凭证引用，第 205 行提出运行级受限权限，但没有定义入口用户、岗位 Agent 和当前运行的授权关系，也没有规定上下文、模型和工具服务如何分别验证。

场景：两个使用者调用同一个岗位 Agent，各自允许读取的企业资料不同；仅凭岗位共享配置无法确定这次运行最终能读取哪部分资料。已发布配置固定了历史授权，撤销某项工具权限后，旧会话的行为也未规定。

需要补充：沿用企业入口传入可验证的调用身份；明确这次运行可用的权限是哪些授权范围的交集；服务端验证的运行身份与凭证作用域；每次资料/工具访问的授权检查；撤权后缓存、已下载资料及活动会话的处理。版本固定负责记录内容，不能把过期授权永久冻结。不需要因此新增浏览器登录页面。

## AR03 · P1：进程隔离尚未形成可执行的安全边界

依据：第 137 行分配独立 profile，第 199、205 行说明独立环境、限制容器管理权限和凭证挂载；未列出 Harness 进程的挂载范围、宿主机权限、网络出口及全局配置继承规则。

场景：Harness 具有 shell、文件和网络工具，即使配置的 MCP 工具范围有限，也可能读取继承的配置/环境、访问其他挂载内容或绕过供应服务直接访问内部系统。

需要补充：每个运行环境的 OS 用户、独立 HOME/配置目录、允许的挂载和持久目录、网络访问范围、资源限制、凭证范围及生命周期；确认所选 Harness 的全局配置、插件和自动加载机制；隔离外部企业操作与平台管理权限。声明配置权限与运行环境的实际能力需要分别验证。

## AR04 · P1：模型版本记录与实际路由尚未绑定

依据：第 114 行固定模型服务和网关配置修订，第 191 行说明先建新部署再切换后续运行，但没有定义 Harness 请求中携带什么标识让 LiteLLM 选中固定的修订，也没有定义旧部署何时可以释放。

场景：旧会话仍使用通用模型名称，网关更新同名路由后，后续一轮请求转到新模型；数据库仍保存旧发布版本，记录与实际调用不符。

需要补充：发布版本引用可解析且不可覆盖的模型部署标识；网关按运行绑定的部署修订路由；记录实际后端；明确旧会话完成、终止或到期前的部署保留规则；资源不足时明确阻止升级或终止旧会话，不能暗中替换。外部供应商可变模型依然需要保留可变标记。

## AR05 · P2：上下文版本没有覆盖完整的索引构建结果

依据：第 78—80 行规定资源有版本、索引建完再切换，第 120 行发布绑定上下文版本；未定义原文版本、切分规则、embedding 模型及版本、索引命名空间和检索参数如何共同组成一个可读取的上下文版本。

场景：同一文档重新切分或更换 embedding 模型后更新检索索引，旧 Agent 发布版本仍指向同一读取入口；文档版本看似没变，实际召回内容已变化，向量维度不一致时还可能无法查询。

需要补充：上下文构建清单与独立索引标识；读取请求绑定清单；发布时切换完整索引版本；明确嵌入服务和重排服务的归属；原文删除、授权撤销与历史快照的处理。实时读取则单独记录来源和读取时间，不伪装成固定快照。

## AR06 · P2：原生会话目录与运行调度的关系尚未确定

依据：第 95、137、179、189 行规定保留原生会话目录，并按原生状态恢复，但未确定一个会话归哪台执行主机、同一个 profile 是否可并发写入、目录存储和备份方式，以及主机失效后的接管条件。

场景：会话第一次运行在主机 A，下一次请求被派到主机 B；数据库中的事件索引不能替代 A 上的原生状态。直接共享目录也不能保证两个 Harness 进程并发写入同一个 profile 是安全的。

需要补充：首版明确会话固定到执行主机及持久卷；profile 与会话的写入归属；失联与主机损坏分别处理；恢复时停止旧写入者、恢复一致目录并核验版本；无法确认时标记不可恢复。明确备份频率及允许丢失的状态范围，不将“目录存在”视为具备容灾能力。

## 修订顺序

先确定 AR01、AR02、AR03：运行如何可靠启动、以谁的权限运行、实际能访问什么；再补 AR04、AR05、AR06 的绑定和状态保存规则。随后选定一种 Harness 与一个模型服务，按这些规则做真实联调。

目前没有证据证明所选开源组件已经作为整套系统运行；本审查不把设计稿中的技术选型视为已验证集成，也不建议仅通过替换图中的工具名称关闭这些问题。
