# 上下文与模型供应：使用及运维

[返回项目](../../README.md) · [岗位 Agent](../position-agents/README.md) · [架构方案](../architecture/README.md)

[本轮验收记录](validation/README.md)。

平台现在有三个关联的交付物：有版本的上下文配置、可以调用的模型服务、固定了 Harness 与这两项依赖的 Agent 发布包。原八个业务模块仍可使用，入口收在“现有业务工具”。

## 上下文供应

1. 在“上下文供应 → 从文件导入资料”上传文件，填写资源名称并提交。
2. 在供应作业中核对状态；解析失败会保留失败原因，不创建空白资源。
3. 完成后点击“刷新资源库”，将资源加入供应配置，设置必选项、权限和字符预算。
4. 在岗位 Agent 发布中引用配置。已有候选版本固定原资料；更新资源后需要更新供应配置并生成新候选版本。

支持 5 MB 内的 UTF-8 文本、Markdown、CSV、JSON、DOCX 和可提取文本的 PDF。PDF 最多 500 页；提取结果不超过 20 万字符。CSV/JSON 作为原文本供应，不自动解释业务结构；扫描件需要先 OCR。当前解析器为标准库与 pypdf，没有部署 Docling、向量索引或自动来源同步。

上传原文件、SHA-256、解析版本和新资源标识相互关联，记录在作业中。MCP、控制台新接口和旧兼容接口读取同一资源库；只读配置继续固定资源版本，笔记写入仍需显式授权并检查版本。

## 模型供应

### 已有模型服务

在“模型供应 → 登记模型服务”填写实际地址、模型标识、上下文及输出上限。密钥保存在后端私有文件，不回显。登记完成只表示配置已保存；是否支持工具调用及岗位任务，须通过真实 Agent 试运行核对。

### 自有模型

1. 保存训练数据集：上传 JSON 数组，每条包含 `instruction`、`output` 和可选 `input`，最多 10 MB、10 万条。校验后生成独立数据集记录与摘要；重新上传创建新记录，不覆盖旧快照。
2. 登记本机基础模型：选择后端实际存在的模型目录。完整权重须包含 `config.json` 和权重文件；LoRA 目录须包含适配器配置与权重。系统不自动下载权重。
3. 提交 LoRA 训练：选择数据集、基础模型、对话模板、轮次与学习率。后台生成受控配置，通过 LLaMA-Factory 原生 CLI 执行 SFT；实际日志保存到作业目录。
4. 核对产物：只有进程正常退出且存在产物文件才登记新 LoRA 模型，并关联来源作业、基础模型和数据集。
5. 合并导出：选择 LoRA 产物，通过 LLaMA-Factory 导出完整模型，形成新的产物记录。
6. 部署：选择完整模型、可用端口与模型支持的 vLLM 工具调用解析器。后台启动仅监听本机的 vLLM，核对 `/v1/models` 返回的实际模型标识后才登记模型服务。服务进程由作业持续监管，退出会标为失败。
7. 为岗位生成新候选版本，试运行后采用。部署就绪只证明服务启动，不证明模型质量或工具调用正确。

JSON 数据示例：

```json
[
  {"instruction": "这笔报销需要谁审批？", "input": "金额：6800 元", "output": "按示例制度，应提交经理审批。"}
]
```

训练示例不代表企业实际制度。不同模型需要匹配其对话模板与工具调用解析器；未启用或不支持工具调用的服务无法完成 Pi 的上下文工具流程。

### 独立的软件环境

核心 API/worker 安装 `requirements-core.txt`，不要求加载 Torch、Gradio 或图服务。原业务工具继续使用 `requirements-platform.txt`；训练和推理可独立安装在匹配硬件的 Python 环境中：

```bash
export WORKBENCH_TRAIN_PYTHON=/srv/envs/training/bin/python
export WORKBENCH_INFER_PYTHON=/srv/envs/inference/bin/python
./start_console.sh
```

这两个路径来自启动配置，页面请求不能指定任意命令。未设置时使用后端当前 Python。“运行环境”检查包版本；安装不等于显存、驱动和模型都满足要求。当前本机没有 vLLM；不会把未执行的部署标成可用。

训练/导出协议按现有 LLaMA-Factory 0.9.1 接入；推理使用 vLLM OpenAI 服务入口。升级原生组件后须重新验证适配与模型组合，不能仅凭包名判断兼容。接口依据：[LLaMA-Factory](https://github.com/hiyouga/LLaMA-Factory)、[vLLM 在线服务](https://docs.vllm.ai/en/latest/serving/online_serving/)。

## 作业与进程

一个 `platform_worker` 进程持有本机文件锁，分别处理岗位运行队列与供应作业队列。岗位一次运行一个 Pi；供应作业最多两个并发，长训练不阻塞 API 或岗位队列。部署持续占用一个供应作业槽，不代表自动 GPU 调度；同机资源不足时应停止推理再训练。

供应作业提供排队、执行、完成、失败、中断、取消和服务运行中状态，保留实际原生命令、组件版本、日志与结果。重复的同一请求标识不会创建第二份作业。取消运行中的作业会停止其原生进程组；已经作为岗位默认版本依赖的部署，需要先为相关 Agent 采用其他模型，才能从页面停止。

退出启动器会停止其 worker 及受管模型进程；它不会自动停止独立 PostgreSQL。重启后未完成的作业标为中断，不自动重训、重新导入或重启推理。历史模型服务可能已停止，旧版本只供追溯；新候选不能选用已经停止的受管部署。

## 数据、迁移与备份

岗位、上下文、模型与供应作业共用 `WORKBENCH_DATABASE_URL` 指向的数据库，默认读取 `.workbench/database-url.txt`。统一启动脚本未发现数据库配置时，建立 SQLite 开发连接文件；正式单机使用 `tools/start_platform_db.py` 初始化 PostgreSQL，配置方式见根 README。

第一次进入新上下文库时，从旧 `context-supply-v1.sqlite3` 复制资源、配置与审计，保留原 ID、全部版本和授权信息，写入迁移标识；同时创建 `context-supply-v1.sqlite3.pre-platform.bak`。原文件不删除，后续通过新服务统一读写目标库。不要再运行旧版本服务写旧文件，否则会形成两份相互不更新的记录。

| 保存位置 | 内容 |
| --- | --- |
| 数据库 | 岗位、Agent、上下文各版本、供应审计、数据集/模型元数据、发布、运行与作业 |
| `.workbench/datasets/<id>/` | 固定训练数据、LLaMA-Factory 数据描述 |
| `.workbench/jobs/<id>/` | 上传原件、原生配置与命令、日志、进程记录和训练/导出结果 |
| `.workbench/agent-workspaces/<id>/` | Pi 的独立配置、上下文、原生会话和结果 |
| `.workbench/model-credentials/` | 私有模型调用凭证 |
| 原模型登记路径 | 操作员提供的本机基础权重或 LoRA，平台不复制或删除 |

备份时先停止本项目执行进程，使用 PostgreSQL 的 `pg_dump`，并一起备份 `.workbench/` 文件与外部登记的模型目录；只有数据库备份不能恢复全部原件、会话和权重。SQLite 开发环境停机后复制整个状态目录。连接文件和凭证属于私有数据，不提交 Git。

## 当前边界

本轮补齐的是统一存储、文件导入和 LoRA 到服务登记的作业连接。原 CPT/DPO、偏好和模型评测仍在“现有业务工具”；自动同步、向量检索、MLflow、其他 Harness、原生会话续接没有接入。测试中的协议服务和微型权重仅用于验证调用链，不作为业务质量证据。
